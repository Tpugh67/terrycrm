# ADR 0002: Configuration-driven industry pages

**Status:** Accepted
**Date:** 2026-07-19

## The problem

18 industry landing pages existed as 18 separate hand-written files
(`real-estate/page.tsx`, `insurance/page.tsx`, etc.), flagged as
duplicated code back in the Pass 1 audit. Each was 108–176 lines of
near-identical structure: nav, hero, an interactive demo pipeline board,
an optional feature grid, a closing CTA, and a footer — with only the
copy, demo data, and pipeline stages actually differing between them.
Changing the shared layout (e.g. adopting the Pass 2–4 design system)
would have meant editing the same structural change 18 times, with high
risk of the pages drifting from each other over time exactly the way the
homepage had already drifted from them.

## The decision

Replace the 18 static page files with:

1. **`src/lib/industryPages.ts`** — one config file, one entry per
   industry, containing every real per-industry value: hero copy, demo
   pipeline stages and deals, and (where they existed) feature
   descriptions.
2. **`IndustryPageTemplate`** — one component that renders that config
   through the existing marketing component library (`HeroSection`,
   `FeatureGrid`, `CTASection`) plus one new component,
   **`IndustryDemoBoard`**, which generalizes the interactive
   "click a stage, filter the board" demo that existed, separately
   hand-built with slightly different field names, on all 18 original
   pages.
3. **`src/app/(marketing)/[industry]/page.tsx`** — a single dynamic route
   with `generateStaticParams` returning all 18 slugs. URLs are
   unaffected (`/real-estate`, `/insurance`, etc. still resolve exactly
   as before); the 18 folders are gone, replaced by one route + one
   config file.

The homepage's own industry grid was *also* independently hardcoding
this same label/icon/color/route data — it now derives from the same
`industryPages.ts` config instead of maintaining a second, separately-
drifting copy.

## Why this was chosen over alternatives

**Alternative 1 — keep 18 files, just restyle them with the new design
system.** Rejected. This fixes the visual inconsistency but not the
actual problem: 18 copies of the same layout logic, still one edit away
from drifting apart again. It also would have meant manually rewriting
~2,700 lines of JSX by hand across 18 files, with no structural guarantee
they'd stay identical afterward.

**Alternative 2 — invent new, more polished copy for all 18 industries
while consolidating.** Rejected. The original 18 pages already contained
real, specific, well-written content (accurate industry terminology,
believable example deals clearly labeled as a demo). Discarding that in
favor of AI-generated replacement copy would have been a strict content
downgrade and, more importantly, would have meant fabricating example
data rather than reusing what a human had actually authored. Real content
was extracted programmatically and verified (see Verification below), not
rewritten.

**Alternative 3 — keep the interactive demo boards as 18 separate
components.** Rejected once the extraction showed how consistent the
underlying shape actually was: every page had exactly 5 stages, 5 demo
deals, and one of a small number of field-naming conventions (`seller`/
`arv`/`asking`/`spread` for real estate; `client`/`premium`/`commission`
for insurance; a generic `client`/`value`/`commission` shared by 13 of the
18). One component parameterized by a normalized `DemoDeal` shape covers
all of them.

## Consequences

**Positive:**
- Zero duplicated layout code across 18 pages — the Pass 1 audit finding
  this was written to resolve.
- Adding a 19th industry is now: one new config entry, zero new page
  files, zero new layout code.
- The homepage's industry grid and the industry pages themselves can
  never drift apart from each other again — same config, one source.
- Every industry page now inherits the Pass 2–4 design system
  automatically (tokens, `Card`, `Badge`, motion) rather than needing 18
  separate migrations.

**Negative / risks accepted:**
- The config was generated by a script parsing the original 18 files'
  JSX, not hand-transcribed. This is faster and less error-prone than
  manual copy-paste across 18 files, but it means the config's accuracy
  depends on the extraction script being correct — mitigated by
  programmatically verifying, post-build, that every one of the 18
  generated static pages actually contains its real extracted content
  (not just that the build succeeded) rather than trusting the build's
  exit code alone.
- The two industries that had a `features` section (real estate,
  insurance) keep it; the other 16, which never had one in the original
  pages, still don't. The template supports it but doesn't fabricate
  content to fill the gap for industries that never had it.
- `IndustryDemoBoard`'s stage-color assignment cycles through a fixed
  5-tone sequence rather than reading meaning from each industry's
  specific stage names — acceptable for a demo visualization, flagged in
  case a future pass wants stage colors to carry more specific meaning.

## A real bug this surfaced, unrelated to the architecture decision itself

Next.js 16 changed dynamic route `params` to a `Promise` that must be
awaited — the first version of `[industry]/page.tsx` used the older
synchronous-access API. The build reported success and even listed all 18
static paths as generated, but every one of them silently rendered as an
error boundary (`id="__next_error__"` in the output HTML) instead of real
content. This was caught by writing a follow-up verification step that
checks generated HTML for actual expected content — a successful `next
build` exit code alone was not sufficient evidence the pages worked.
Fixed by awaiting `params` in both `generateMetadata` and the page
component; re-verified afterward, confirmed all 18 pages render real
content.

## Follow-ups this ADR intentionally does not resolve

- Whether `industryConfig.ts` (the separate, pre-existing CRM
  pipeline/stage configuration used by the actual in-app pipeline pages)
  should eventually be merged with or referenced by
  `industryPages.ts` (this marketing-page config) — they currently
  overlap in spirit (both are "per-industry data") but serve genuinely
  different consumers (in-app CRM behavior vs. marketing page content)
  and were kept separate rather than conflated.
- Per-industry `dashboardPreview`/`ProductScreenshot` usage on these
  pages — not added in this pass, same real-screenshot dependency
  flagged in every previous pass.
